Judge guide

Kitebase is a fictional SaaS business. It sells plans through PayPal Sandbox checkout, keeps its own database, and is connected to SettleIQ only through SettleIQ's connectors: PayPal webhooks and reads, a read-only database role, and a role that can correct one column of its payments. The sign-ins for SettleIQ and the PayPal Sandbox buyer account come with the submission; they are not published here.

Before you start

  1. On Demo controls, press Queue both so the next two checkouts each carry one fault.
  2. In SettleIQ, open Playbook Requests as the Tenant Owner and check both scopes in the Execution mode panel read SHADOW. Use Return to SHADOW if an earlier run left one LIVE.

1. Lost confirmation (PB-001)

  1. On Plans, check out any plan with the PayPal Sandbox buyer. The shop reports it could not confirm the payment.
  2. On Sources, PayPal shows the capture COMPLETED while Kitebase's payment is still PENDING.
  3. In SettleIQ, as the Domain Operator: sync the Kitebase database source, then run the Financial Operations domain run. A STATUS_MISMATCH case appears.
  4. Investigate the case, then request PB-001 from it. Sign in as the Approver and approve.
  5. While the merchant-correction scope is SHADOW, the request is POLICY_BLOCKED and nothing changes here.
  6. As the Tenant Owner, switch merchant.payment_status.correct to LIVE. The blocked request runs, and on Sources the payment reads COMPLETED and the subscription becomes active.

2. Double charge (PB-002)

  1. Check out again. The shop reports a timeout; pay again when it asks. PayPal now holds two captures for one order, shown on Sources.
  2. In SettleIQ, run Financial Operations again. A DUPLICATE_CAPTURE case appears with the proof.
  3. Investigate, request PB-002 and approve it as the Approver.
  4. As the Tenant Owner, switch refunds.create to LIVE. SettleIQ refunds the later capture in PayPal Sandbox; on Sources it reads REFUNDED and the original capture is untouched.

3. Subscription billing (SaaS pack)

  1. On Sources, two subscriptions are flagged: one active for a month with no paid invoice, one paid a year ahead but never extended.
  2. In SettleIQ, run the SaaS Subscription Lifecycle domain run. Two RENEWAL_INVOICE_MISMATCH cases appear. This pack only detects: it has no action and no execution-mode scope.

Run it again

Queue both faults again on Demo controls and return both scopes to SHADOW. The next two checkouts are new orders with new discrepancies; nothing earlier is deleted, so SettleIQ keeps reconciling every order it has already seen.
